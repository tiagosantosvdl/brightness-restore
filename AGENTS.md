## Behavior to preserve

- Valid normalized brightness is finite and within 0..1, including zero.
  Missing backends/properties and negative or invalid readings are unavailable,
  not percentages to display or values to save.
- Both indicator styles start hidden and become visible only after a valid
  reading. Standalone mode also hides its slider and closes its menu when
  unavailable. Quick Settings controls visibility through its indicator actor.
- Unavailable readings cancel pending saves and do not replace saved brightness.
  Brightness writes and slider requests are guarded against unavailable readings.
- The preferred backend is `Main.brightnessManager.globalScale` when available;
  the fallback is the SettingsDaemon Power Screen D-Bus `Brightness` property.
- Keep restore-on-startup, debounced persistence, preference synchronization,
  indicator positioning, idle screen blanking, and wake restoration intact.
- Clean up signals, timeouts, idle monitoring, and overlays on disable. Backend
  replacement on monitor hotplug and asynchronous initialization across disable
  are not covered by committed regression tests; do not claim they are verified.

## Verification

Use checks appropriate to the change:

```sh
node --input-type=module --check < extension/extension.js
node .scripts/validate-build.js
node .scripts/scan-leaks.js
glib-compile-schemas --strict --dry-run extension/schemas
python3 -m unittest discover -s tests -p '*test.py'
git diff --check
```

- Syntax-check every changed JavaScript file. Shell sources require ES module
  parsing; the release workflow checks all JavaScript under `extension/` via stdin.
- `tests/release_package_test.py` exercises real ZIP and Debian builds, payload
  equality, checksums, ownership/permissions, version validation, prerelease
  ordering, compiled-schema requirements, and GNOME Shell dependency ranges.
- The original brightness fix passed temporary mocked regression checks for both
  indicator styles, invalid readings, zero, failed connections, missing properties,
  and persistence guards. These checks were not saved as a committed test suite.
- `npm run lint` and `npm run lint:fix` currently suppress ESLint failures using
  `|| true`. Do not treat their exit status as proof that lint passed. When
  dependencies are available, run ESLint directly and inspect its result.
- `build.sh` installs into the user's desktop and changes extension/schema state;
  it is not a harmless verification command. `package.sh` also rewrites source,
  version metadata, formatting, lint fixes, and documentation.
- `make release` stages in ignored `_build/` and creates packages in ignored
  `dist/` without installing. Use it for package verification.
- Automated or mocked checks do not establish live GNOME behavior. Use isolated
  temporary configurations and memory-backed settings for tests; never fall back
  to live dconf writes to make a diagnostic pass.
